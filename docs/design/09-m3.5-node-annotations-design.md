# M3.5 — Node (Entity) Annotations (design / spec)

Status: **Approved** · Date: 2026-07-09

Expands the node-annotation slice deferred from M3 (see
[`07-m3-inline-annotations-design.md`](07-m3-inline-annotations-design.md) →
"Deferrals") into an execution-ready design. Builds on M2 (Tree) and M3 (Inline
Annotations). The task-by-task plan is produced separately from this spec.

## Goal

Let the document owner attach **one Markdown note + freeform tags to a whole
tree node** (a proposition, paragraph, chapter — any node the tree defines).
Unlike an inline highlight, a node note anchors to the node itself, not to a span
of source text, so it is **translation-agnostic** (shows regardless of which
translation is visible) and needs no offset math. Each node carries a small
**left-gutter marker**: a faint hollow dot when the node has no note, a solid dot
when it does. Clicking the marker expands the note **beneath the node's content**
(terminal-style, mirroring `InlineNote`) — read as rendered Markdown, or edit if
you are the owner.

## Scope (and explicit cuts)

**In:**
- `node_annotations` schema (entity-level, one per node per author).
- `getDocument` loads node annotations and attaches each node's own note to its
  `TreeNode`.
- `NodeAnnotationMarker`: the gutter dot (hollow / solid), the reveal affordance.
- `NodeNote`: terminal-style note that expands beneath the node; Markdown-rendered
  view + owner editor (note / tags / delete).
- Server Actions: **upsert** (create-or-edit, honoring the unique constraint) and
  delete, gated so a user creates on documents they can access and edits/deletes
  only **their own** note.
- Markdown rendering via the `react-markdown` + `remark-gfm` already added in M3.

**Out (deliberate cuts, deferred):**
- **Threaded comments** — M5.
- **Author markers, author filter, and rendering _other_ users' node notes** —
  M5. M3.5 is single-user: the only author is the owner, so "mine vs. theirs"
  does not yet exist. The per-node field is **singular** now (`nodeAnnotation:
  NodeAnnotationView | null`) and becomes a list in M5.
- **Color** — node notes have no color by schema (unlike inline highlights).
- **Cross-linking annotations/nodes** — V1 cut (see [`02-annotations.md`](../02-annotations.md)).

## Data layer

New table, exactly per [`01-data-schema.md`](01-data-schema.md):

### `node_annotations`
- `id uuid pk`
- `document_id uuid → documents.id` (cascade)
- `node_id uuid → nodes.id` (cascade)
- `author_id text → users.id`
- `note text not null` — Markdown. A node note **is** its note; there is no
  null "just a marker" state (contrast `inline_annotations`, where the highlight
  can exist with a null note).
- `tags text[] not null default '{}'`
- `created_at`, `updated_at`
- **`unique (node_id, author_id)`** — one note per author per node. A node's
  further discussion continues in its M5 comment thread, not in multiple root
  notes.

Indexes: `(document_id, author_id)` (author filter is M5, but the index is cheap
and additive now); GIN on `tags`. Migrated with `pnpm db:push`.

**Immutability invariant unchanged:** node notes reference a `node_id`, never
`sources.text`; nothing updates `sources.text`.

## Why this milestone is simpler than M3 / M4

A node note anchors to the **node**, not to a character span, so:
- **No offset model.** No DOM Range → offset mapping, no `splitSpans`, no
  rebasing. Attachment is a `Map<nodeId, note>` lookup.
- **No source scoping.** Because node notes are translation-agnostic, they load
  per-**document** (`where documentId = …`), not per-source. This sidesteps the
  primary-source coupling that `getDocument` carries for ranges and inline
  annotations, and that M4 must still resolve.

## Shared type

Alongside `InlineAnnotationView` in [`lib/annotations/types.ts`](../../lib/annotations/types.ts):

```ts
export interface NodeAnnotationView {
  id: string;
  nodeId: string;
  note: string;
  tags: string[];
  authorId: string;
}
```

## Read pipeline changes

- `TreeNode` (in [`lib/tree/build.ts`](../../lib/tree/build.ts)) gains
  `nodeAnnotation: NodeAnnotationView | null`. Singular in single-user M3.5 (at
  most the owner's one note); becomes a list in M5.
- `buildTree(nodes, ranges, sourceText, inlineAnns?, nodeAnns?)` gains an optional
  node-annotations argument and attaches each node's own note by `nodeId` via a
  `Map` lookup. No offset math; nodes with no note get `null`.
- `getDocument` selects the document's `node_annotations`
  (`where(eq(nodeAnnotations.documentId, doc.id))`), maps rows to
  `NodeAnnotationView`, and passes them to `buildTree` as the new argument. Loaded
  per-document, so unaffected by which source is primary.

## Server Actions — `lib/actions/nodeAnnotations.ts`

Mirrors the structure of [`lib/actions/annotations.ts`](../../lib/actions/annotations.ts).

- `upsertNodeAnnotation({ documentId, nodeId, note, tags }): Promise<string>`
  - `requireUser()`, then `authorize(user.id, documentId, "annotate")` — create
    requires document access (owner today; M5 widens to collaborators).
  - Rejects a whitespace-only `note` with `"Note required"` (mirrors the not-null
    invariant).
  - `insert(...).onConflictDoUpdate({ target: [nodeId, authorId], set: { note,
    tags, updatedAt } })` — the unique constraint makes create and edit the **same
    operation**, so one action serves both. Returns the row id.
- `deleteNodeAnnotation(id): Promise<void>`
  - Author-gated via a local `loadOwnNodeAnnotation(id)` that loads the row and
    throws `"Not found"` / `"Forbidden"` — mirrors `loadOwnAnnotation` in
    `annotations.ts`.

Both `revalidatePath('/d/[docId]')`.

### Authorization
Reuses the existing [`authorize`](../../lib/auth/authorize.ts) (owner-only today)
for create, plus an inline `authorId === userId` check for edit/delete. This is
the M3.5 slice of the [`02-frontend-and-permissions.md`](02-frontend-and-permissions.md)
matrix; M5 widens `authorize` to the full role matrix (collaborators create own
notes, never touch structure).

## Interaction (client islands)

### `NodeAnnotationMarker` (gutter dot, one per node)
Rendered by `NodeSection` for every node. Anchored absolutely in the left gutter
like `.tree-controls`, but on its own slot so the two never collide.
- **Empty node:** faint hollow dot (`◦`, `var(--muted)`), **always rendered**
  (not hover-gated, so it works on touch); brightens on node hover.
  `aria-label="Add note"`. Click → open `NodeNote` in edit mode.
- **Node with a note:** solid dot (`●`, `var(--ink)`), always visible.
  `aria-label="Note"`. Click → open `NodeNote` in view mode.
- On mobile (`<860px`), `.tree-controls` is hidden (owner-restructure feature) but
  the note dot **stays** — node notes are a reader feature, not a restructure one.

### `NodeNote` (expands beneath the node's content)
Reuses the `.inline-note` marginal-apparatus CSS, but with a neutral
`var(--rule)` left border instead of a highlight color (node notes have no color).
- **View mode:** `react-markdown` + `remark-gfm` rendered note, tag chips, and
  (owner only) an `Edit` button + `Close`.
- **Edit mode:** note `textarea` (Markdown, **required** — empty blocks Save), tag
  add/remove (same controls as `InlineNote`), `Save` / `Cancel` / `Delete`.
  Save → `upsertNodeAnnotation`; Delete → `deleteNodeAnnotation` then close.
- "Is the note open" is **local `NodeSection` state** (`useState`), the same
  pattern `SourcePassage` uses for `openId`. Empty nodes open straight into edit
  mode; noted nodes open in view mode (mirrors `InlineNote`).

### `NodeSection` wiring
`NodeSection` reads `node.nodeAnnotation` from the tree and renders
`<NodeAnnotationMarker note={node.nodeAnnotation} canEdit={canEdit} onOpen={…} />`
in the gutter and, when open, `<NodeNote node={node} annotation={node.nodeAnnotation}
canEdit={canEdit} onClose={…} />` after the node's `SourcePassage`.

## Component strategy

`NodeNote` is a **sibling** to `InlineNote`, not a generalization of it. Inline
notes carry color swatches, source offsets, and an overlap picker — none of which
node notes have. Sharing the whole note component would grow conditional branches
over two genuinely different shapes. We share the **CSS** (`.inline-note` marginal
style) for visual consistency, not the note component, keeping each readable in
isolation.

The one genuinely shared piece is the **tag editor** (the tags list + add/remove
+ text input), which is identical for both note kinds. That is extracted into a
small `components/TagEditor.tsx` (`{ tags, onChange }`) and consumed by **both**
`InlineNote` (refactored from its inline copy) and `NodeNote` — so the shared
logic lives in one place while each note component keeps its own distinct shell
(recolor swatches for inline; required-note / delete semantics for node).

## Testing

Per the project's execution preference, implementation and tests are written
together with a single final green run (no separate RED step).

- **Schema (Neon test branch):** insert/read round-trip with tag/timestamp
  defaults; the `unique(node_id, author_id)` conflict **updates** rather than
  duplicating; cascade delete when the node/document is removed.
- **`buildTree` unit:** attaches the matching node's note by `nodeId`; leaves
  other nodes `null`.
- **Server actions (Neon):** upsert creates then updates the same row (exactly one
  row after two calls); empty note → `"Note required"`; wrong-owner create →
  `"Forbidden"`; non-author delete → `"Forbidden"`.
- **Component:** `NodeAnnotationMarker` renders hollow vs. solid by presence of a
  note; `NodeNote` renders Markdown + tags in view mode and calls
  `upsertNodeAnnotation` with the edited note + tags on Save.
- **E2E (Playwright) happy-path** stub; the live in-browser click-through remains a
  human TODO, consistent with M1–M3 (headless runs cannot fully exercise hover /
  tap reveal across viewports).

## Acceptance

On `/d/[id]`, signed in as the owner:
1. Every node shows a faint gutter dot; click one → an editor expands beneath that
   node; type a Markdown note + a tag, Save → the dot goes solid and the rendered
   note persists across reload.
2. Click a solid dot → the note expands in view mode with rendered Markdown + tag
   chips.
3. Edit the note → the change persists, and exactly **one** row exists for that
   node (re-saving does not duplicate).
4. Delete the note from its editor → the dot returns to hollow, the note
   disappears, and both persist across reload.
5. All of the above work on a **leaf prose paragraph that has no heading** (the
   case the gutter-marker anchor was chosen to cover).

## Deferrals & coupling notes (tracked)

- **Singular field seam:** `TreeNode.nodeAnnotation` is `NodeAnnotationView | null`
  for single-user M3.5. M5 flips it to `nodeAnnotations: NodeAnnotationView[]` and
  the marker becomes a count/stack; the load query drops its implicit single-author
  assumption. Named singular now to signal the future shape without building for it.
- **`authorize` is owner-only today;** M5 extends it to the full membership/role
  matrix (collaborators create own notes, never restructure).
- **Threaded comments** attach to a `node_annotation` target in M5
  (`comments.target_type = 'node_annotation'`).
